## Porque é que isto é necessário, e não opcional

A procedure `P_ALIM_ENG_CORP_P1_BIS` começa por **esvaziar a tabela**:

```sql
DELETE FROM ENG_CORP_P1_BIS;
```

A tabela guarda, portanto, **só o arrêté corrente**. Sem historização, o arrêté
anterior desaparece na corrida seguinte — e desaparece **sem erro**.

Isto impõe uma ordem na cadeia mensal: a extração para o HCRR tem de correr
**depois** de a tabela estar cheia e **antes** do `DELETE` da corrida seguinte.

## O que já se sabe da tabela (medido)

| | |
|---|---|
| colunas | **668** — 663 da Notice V45 do P1 + 5 técnicas |
| por tipo | 463 `VARCHAR2`, 162 `NUMBER`, 43 `DATE` |
| largura máxima de uma linha | **6 259** octetos |
| linhas por arrêté | **122 225** (as linhas P1 do `CRRCORP.dat`) |
| alimentadas pela procedure | 296 colunas; as outras 367 ficam `NULL` |

**Volume**, se o histórico for uma cópia da tabela por arrêté:

```
no maximo declarado   730 MB por arrete  ->  12 meses   8,5 GB
a 30% de ocupacao     219 MB por arrete  ->  12 meses   2,6 GB
```

A estimativa a 30% é a mais realista, porque **367 das 668 colunas ficam `NULL`**
— são os campos que a V45 criou e ainda não têm origem. Mas é estimativa: só a
`DBA_SEGMENTS` depois de uma carga dá o número a sério.

**A chave natural** para o histórico é a que o `TESTES.sql` já usa para emparelhar:

```
DT_ARRETE + ID_ENGAGEMENT + CD_PERIMETRE + NO_VARIANTE
```

A `ID_ENGAGEMENT` sozinha **não** serve: a mesma pode dar mais do que uma linha,
porque as 8 variantes podem apanhar o mesmo engagement. A tabela já tem a
`DT_ARRETE`, por isso o histórico pode ter a mesma estrutura, sem coluna nova.
